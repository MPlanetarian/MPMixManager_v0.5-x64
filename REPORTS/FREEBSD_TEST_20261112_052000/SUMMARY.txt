1. HOST PATCH UPGRADE
======================================================================
  This VM uses **pkgbase** (packaged base), so `freebsd-update` refuses to
  run ("incompatible with the use of packaged base"). The correct upgrade
  path is the FreeBSD-base pkg repository:

    pkg update -f
    pkg upgrade -y -r FreeBSD-base      # 111 packages
    # reboot to load the patched kernel
    pkg upgrade -y                      # remaining ports (156 packages)

  Before : 15.1-RELEASE        (releng/15.1-n283562)
  After  : 15.1-RELEASE-p6     (releng/15.1-n283643-95719d8a895b)

    freebsd-version -kru  ->  15.1-RELEASE-p6 / 15.1-RELEASE-p6 / 15.1-RELEASE-p6
    uname -a              ->  FreeBSD X299ROGFREEBSD 15.1-RELEASE-p6 ...
    pkg upgrade -n        ->  "Your packages are up to date."

  Kernel and userland both rebooted into p6 and verified live.

  NOTE: the VM shipped without any audio hardware, so it was restarted with
  a QEMU `ich9-intel-hda` + `hda-output` device. Without this the guest has
  `hw.snd.default_unit: -1` and no `/dev/dsp*`, and no audio test is possible.
  This is a test-bed change only; it is not an application requirement.

5. DEFECT FOUND AND FIXED
======================================================================
  [FIXED] Traktor S4 MIDI daemon crashed on FreeBSD at every start.

    Symptom: every manager launch appended a traceback to
      ~/.config/mix-manager/traktor_s4_midi.log
        FileNotFoundError: [Errno 2] No such file or directory: 'amidi'
      and the MIDI service died immediately. `--status` then reported
      "MIDI Service Daemon: Disabled / Stopped".

    Cause: FreeBSD has no ALSA. There is no `amidi` binary and no
    /dev/snd/midi* tree; MIDI arrives through umidi(4) as /dev/umidi* or
    /dev/midi*. `run_amidi_stream()` unconditionally spawned
    `amidi -p hw:0,0 --dump`, and `detect_traktor_s4_port()` also assumed
    /proc/asound and amidi exist.

    Fix (scripts/traktor_s4_midi.py):
      * `run_amidi_stream()` holds in a clean standby loop when `amidi` is
        unavailable, writes status "standby" with the reason, and never
        raises. It also no longer spawns a subprocess in that case.
      * `detect_traktor_s4_port()` only calls `amidi -l` when the binary
        exists, and scans /dev/umidi* + /dev/midi* on FreeBSD.
      * `_get_rawmidi_device_path()` maps the port to a umidi(4) device on
        FreeBSD instead of building a /dev/snd/midiCxDy path.
      * `--status` prints a "MIDI Port ... (umidi(4): /dev/umidi* or
        /dev/midi*)" row on FreeBSD instead of claiming an ALSA port; the
        built-in guide does the same.

    Verified: `--start` now prints "successfully started" and `--status`
    shows "✓ Active & Running" in standby, with a single informative log
    line and no traceback. 17/17 tests pass on FreeBSD and on Linux
    (`python3 -m unittest tests.test_traktor_s4_midi`).

6. OTHER NOTES (test-bed, not product defects)
======================================================================
  1. [TEST BED] The VM had no audio device. QEMU was restarted with an
     ich9 HDA line-out so audio could be exercised at all.
  2. [TEST BED] This FreeBSD image has no compositor-independent terminal
     font control: GNOME Console shipped with `font-scale 4.0`, which made
     the first MP Mix Manager window show only 3 menu rows. Setting it to
     1.0 restored a normal 118-column console. The app rendered correctly
     either way — only the number of visible columns changed.
  3. [TEST BED] `konsole` was not installed, and the `.desktop` entry sets
     `Terminal=false`, so the manager console opened in the desktop's
     default terminal. konsole was installed to match the documented
     launcher; the shortcut works with either.
  4. [DEPENDENCY] The tray icon needs PySide6. `pkg install py312-pyside6`
     was required; before that the tray shell printed
     "tray: no python3 on this host can import PySide6; not starting" and
     exited 0. Worth adding to the FreeBSD prerequisite list in the README
     alongside py311-gobject3 and py311-numpy (which are themselves stale
     names on a py312 system).
  5. [SOFTWARE RENDER] There is no GPU passthrough, so OpenGL runs on Mesa
     llvmpipe. The player and visualizer are correct but slow; performance
     numbers here are not representative of real hardware.
  6. [HARNESS] Sending `Z` to the player with xdotool does not reach the
     player's key handler, because that handler reads the embedded VTE pty
     rather than the X window. The visualizer launch path itself was
     verified directly (`launch_liquid_visualizer()` -> True, window mapped,
     new preset selected), so this is a limit of the automation, not of the
     feature.
